================================================================================
 SCENARIO 1 - CONSTRAINT-BY-CONSTRAINT: CODE vs MODEL  (MULTI-DAY RECEDING)
================================================================================
Compares what the Julia code enforces against the formal model (math_model.tex /
the source "Optimization.pdf") and Avik's reference MCS_OPTIMAL_v4_real.jl. The
cross-day window MILP is built in code/3_MCSModel.jl (build_window_model); the
multi-day closed loop is code/4_MPCLoop.jl (run_mpc); the entry point is
code/6_Receding_Horizon_main.jl.
code/4_MPCLoop.jl also has run_one_shot (Approach 0): the SAME build_window_model,
solved ONCE per day (at that day's 8:00) and replayed open-loop for the day, so
every row below applies to Approach 0 unchanged -- the difference is purely how
often the MILP is solved (once/day vs every 15 min), not what it enforces. Approach
0 needs no buffer day (each day's own window already ends at the next day's 8:00).

Controller: MULTI-DAY, CROSS-DAY RECEDING horizon. The loop simulates D_total =
n_days + 1 days (n_days reported + 1 dropped BUFFER day) at 15-min steps. Each step
re-solves a CROSS-DAY window MILP over K_win = [global k0 .. end of daytime block
min(D_total, day + lookahead_days)] laid end to end; only the FIRST interval is
applied and the window recedes. Each DAY is a daytime block of n_day intervals
(n_day = n_int = 96, the FULL 24 h). NIGHTS ARE INTERVALS of the same MILP: there is
no reset bridge and no phase2_overnight_charge routine. The MCS terminal equality at
b_term (the next day-start) forces the recharge and the TOU price schedules it in the
cheapest hours. Battery state and unfinished work carry over continuously across the
whole run. The buffer day is DROPPED from all outputs.

Power model: FIXED (Fork B). The activity powers are a calibrated Bayesian prior
N(mu, sigma) (the posterior of Avik's offline Python regression). The MILP plans on
mu; the plant samples per-(excavator, activity) powers from a pool pre-drawn from
N(mu, sigma) truncated at 0 (idle sigma=0) -- one draw per occurrence of that
(excavator, activity) pair, shared by every approach that simulates the plant (see
SHARED SAMPLE POOL below). No online re-fitting (observe!/refit! are dormant).

WINDOW GEOMETRY: for a global interval index k, wd(k) = mod(k-1,n_day)+1 is its
position WITHIN its day; dayof(k) = div(k-1,n_day)+1 is which day it belongs to.
Daily profiles (price lambda_whl_elec, carbon lambda_CO2, work-avail R_work) repeat
each day and are indexed by wd(k). "Evening" = the last daytime interval of each
day in the window (wd(k)==n_day).

THE DELIBERATE DEVIATIONS FROM AVIK'S EXACT FORMULATION
--------------------------------------------------------------------------------
 1. (8b) CEV terminal is a FLOOR (>= SOE_ini at the next day-start), not an exact
    equality. A CEV cannot discharge, so under the stochastic plant an exact equality
    can become unrecoverable if a CEV drifts above target; the floor keeps it feasible
    while guaranteeing the fleet ends at least as charged as it began. HARD, with no
    tolerance band and no soft variant. (User choice.)
 2. (12c) The per-day work schedule is an EXTENSION beyond the PDF (which is a single
    lumpsum horizon). The roll-over is handled OUTSIDE the MILP: the loop adds each
    morning's quota to a running backlog (rem_dig .+= quota_dig(day)) and subtracts
    realized work. The MILP sees only that backlog and enforces ONE balance per site
    over k <= k_term, with a SINGLE slack s_miss_work[i,a] (NOT indexed by day-block).

 3. (12c) Work is a PER-DAY schedule (dig_by_day/load_by_day), not a single lumpsum.
    Cumulative-through-end-of-day targets are pinned BOTH sides: soft lower (rolls
    over) + HARD upper (no working ahead). This receding-only cap prevents a day from
    borrowing tomorrow's quota when it can see the future block.
 4. Activity ENCODING: the code uses a 4th explicit "idle" activity (B=[1,2,3,4],
    sum_a u == A, mu <= u[idle]); Avik uses the equivalent 3-activity form
    (B=[1,2,3], sum_a u <= 1, sum_a u + mu <= 1). Functionally identical because
    idle power = 0. (User chose to keep the 4-activity form.)
 5. MPC adaptations that cannot match a single-shot solve: cross-day receding
    re-solves, per-window history seeds (E3), carried-in MCS start position and the
    generalised flow balance, remaining-work targets (rem_dig/rem_load), and the
    carried-in demand peaks (E1).

 6. THE ROLLING COUNTERS DO NOT RESTART EACH MORNING. The shared activity history
    (`hist`) is never reset - the day loop in 4_MPCLoop.jl carries it over explicitly -
    so precedence, pacing and the rest rule all accumulate across the WHOLE run, not
    per day-block. Earlier revisions of the docs claimed a per-day restart ("a night is
    a long break"); no such reset exists. Because the day-block is the full 24 h the
    overnight intervals sit in that history as idle, so a night supplies its own break
    and the rest seam is harmless in practice - but the stated mechanism was wrong.

 7. THE WINDOW TAIL ESCAPES THE WORK QUOTA. The 12c balance counts only k <= k_term,
    so any intervals the window sees BEYOND the day-boundary carry no quota accounting
    at all - they are unconstrained rather than budgeted. Benign (work costs energy and
    earns nothing until the next day's quota is issued), but the implicit no-overshoot
    cap guarantees nothing about the tail.

NOTE vs the SHRINKING sibling: the shrinking model is single-day and LUMPSUM, so it
does NOT add this receding version's per-day work schedule or the buffer day. BOTH
have the implicit hard no-overshoot cap, since both write 12c as an equality against
the remaining requirement; neither has an overnight phase (both are full-24 h MILPs).
On a conflict the shrinking base is ground truth; the receding build only ADDS the
multi-day machinery on top.

DORMANT SCAFFOLDING (present but NOT used by the pipeline)
--------------------------------------------------------------------------------
 The Turing/NUTS learner in 1_Common.jl (activity_power_model, observe!, refit!) is
 kept for future online-learning experiments but is NEVER called: the estimator runs
 in calibrated-prior mode, so mu/sigma ARE the fixed prior throughout the run.

 SHARED SAMPLE POOL (1_Common.jl: ActivityPowerPool / draw_activity_power_pool /
 new_cursor / next_power!): from the frozen mu/sigma, n_samples = 20*(n_days_keep+1)
 samples are pre-drawn per (excavator, activity) pair BEFORE either approach runs
 (the +1 covers Approach 1's dropped buffer day). Each approach gets its OWN cursor
 into the SAME pool (new_cursor), so run_mpc and run_one_shot draw identical numbers
 for identical occurrence sequences without one approach's consumption disturbing
 the other's. A draw is consumed only when that (excavator, activity) pair actually
 occurs that interval (idle, sigma=0, never consumes a slot) - this replaced the
 previous per-interval fresh-randn draw.

CLOSED-LOOP CORRECTNESS (modular code 3_MCSModel.jl / 4_MPCLoop.jl):
 - Rolling rules (rest 12e, precedence 12d, pacing 13) are seeded from a SHARED
   per-CEV applied-activity history for the CURRENT day, so a within-window limit
   cannot "leak" work-runs across the every-15-min re-solves; counters restart each
   morning (a night is a long break).
 - The buffer day (day D_total) absorbs the CEV energy-neutral wrap-up so it never
   lands on a reported day; KPIs and all figures use ONLY days 1..n_days.
 - run_mpc (Approach 1) and run_one_shot (Approach 0) share apply_and_simulate! for
   the apply/draw/advance step, so both approaches update plant state identically;
   only the re-solve cadence (every interval vs once per day) differs.
   write_approach_comparison (5_Output.jl) reports their fully realized outcomes
   side by side (totals + per-day) in approach0_vs_approach1.html.
 - MCS SOE advance now reads the MILP's own SOE_MCS variable directly
   (value(model[:SOE_MCS][m, k0+1])), matching the Shrinking_Horizon sibling,
   instead of a hand-recomputed energy-balance formula -- removes a duplicate
   formula that could silently drift out of sync if 3_MCSModel.jl's battery
   equation ever changes.

================================================================================
 PLANT MODES: :sampled vs :mean  (run_mpc and run_one_shot both take `plant`)
================================================================================
 The MILP is unchanged by the plant mode; only what the plant does with the plan differs.

   plant = :sampled  (default, the original behaviour)
       Realized per-(excavator, activity) power = the next unused pool draw. The
       within-interval activity split may be randomised (multi_activity). Each day's
       plan therefore drifts, with no intra-day feedback to correct it.

   plant = :mean     (new)
       Realized power is PINNED to the same mu the MILP planned on, and each interval
       realizes its single planned activity for its whole length (multi_activity is
       forced off, since a random split would reintroduce randomness). Realized ==
       planned EXACTLY within each day. No pool sample is consumed and no cursor
       advances, so a :mean run cannot perturb a :sampled run sharing the same pool,
       and it is exactly reproducible without a seed.

 Approach 0 with plant = :mean is the PER-DAY MILPs' own optima, chained through the
 real end-of-day carry-over: the deterministic reference, with nothing stochastic
 anywhere. EXACTLY ONE MODE RUNS PER CALL, chosen by run_scenario_1's approach0_plant
 kwarg (default :sampled); Approach 1 is always :sampled. The choice decides what the
 reported A1-vs-A0 gap MEANS:

     A0(:sampled) -> A1   = value of intra-day re-planning (like-for-like plant)
     A0(:mean)    -> A1   = drift AND re-planning together (the net figure)

 and the difference between the two A0 numbers, if you run it both ways, is the cost of
 plan drift alone. approach0_vs_approach1.html labels its own column and blurb from
 res0.plant, so a report always states which comparison it is showing, and carries a
 run-diagnostics table (plant mode, infeasible windows, SOE caps, solve time).

 run_mpc accepts `plant` too, so a fully deterministic closed loop is available for
 debugging. That is the first check to run against the UNEXPLAINED synthetic transit
 gap recorded above: A1(:mean) should track A0(:mean) closely, and a large residual
 there points at closed-loop plan churn / seam handling rather than at the plant.

================================================================================
 AUDIT ITEMS CARRIED OVER FROM THE SHRINKING SIBLING
================================================================================
 A1  work_kW IN THE ANALYST LOG WAS COMPUTED FROM THE WRONG POWER VECTOR (FIXED).
     4_MPCLoop.jl's shared plant step logged
         work_kW = sum(dot(a_real[e], d.true_powers)) / delta_T
     i.e. from d.true_powers -- the Fork-A hidden-truth curve -- while the CEV batteries
     and real_P_work were drained using p_true, the Fork-B pool draw. In :synthetic those
     vectors differ, so the logged work power disagreed with the batteries it was supposed
     to describe. Now computed from p_true. 5_Output.jl never consumed this column, so
     figures and KPI CSVs were unaffected; only run_log.txt / the analyst DataFrame.

 A2  THE CEV SOE BALANCE USED TO BE CLAMPED, AND THE CLAMP CREATED OR DESTROYED ENERGY (FIXED).
     apply_and_simulate! used to end with
         soe_cev[e] = clamp(soe_cev[e] + charged - work_true, SOE_min, SOE_max)
     crediting the FULL realized activity duration to rem_dig/rem_load before this clamp ran.
     If a sampled over-draw would push a CEV below SOE_min, the clamp silently raised it back --
     energy out of nowhere -- and the reported SOE trace stopped being the integral of the
     reported power, while rem_dig/rem_load falsely showed the work as fully done. This was
     invisible in the MILP's own feasibility count, so a run could report "0 infeasible windows"
     while still being physically inconsistent.
     FIXED: the realized dig/load/travel duration is now capped by the energy actually
     available (headroom = soe_cev + charged - SOE_min) BEFORE it is credited -- only the
     affordable fraction of the interval counts toward rem_dig/rem_load, and the SOE trajectory
     never actually needs to be clamped below the floor in normal operation (a clamp() call
     remains only as a safety net). Events are counted as res.n_capped (renamed from
     res.n_clamped), printed at the end of each run, and shown per-run in
     approach0_vs_approach1.html and the sweep summary.

 A3  THE TRAVEL-PACING TWO-SIDED BAND COULD BECOME SPURIOUSLY INFEASIBLE FROM A2's OWN FIX (FIXED).
     A2's fix can leave a small fractional residue in cum_dig_e/cum_load_e (e.g. one interval
     credited as 0.246h instead of a clean 0.25h). The pacing band (13) checks these cumulative
     totals with exact arithmetic and no tolerance, so this residue can land the band's floor
     (kappa*V <= W) and ceiling (W <= kappa*V+kappa) on opposite sides of an integer boundary with
     no whole-interval solution reachable in between -- e.g. needing "between 11.996 and 12.246"
     buckets of work when only whole 0.25h steps are allowed. This permanently blocks further
     travel/work for that CEV, even though the shortfall is physically meaningless (~1 minute).
     Root-caused via HiGHS IIS on the run10_SOE_14.80 sweep point (isolated with a standalone
     repro script + a constraint-bisection harness). FIXED: added pacing_tol = 0.05
     (interval-units) to the floor side only (`kappa*V <= W + pacing_tol`) -- large enough to
     absorb realistic capping residue (~0.02 typical), small enough (5% of one interval) that it
     cannot be mistaken for a free extra work unit or meaningfully weaken the rule's intent.

     SUPERSEDED: pacing now seeds V/W off applied INTERVAL COUNTS (whether the u indicator fired),
     not hours, which removes the fractional residue at its source. pacing_tol is dropped; the
     band is back to the strict `W-kappa <= kappa*V <= W`. This seed is also now scoped to the
     CURRENT CALENDAR DAY only (today_start), unlike precedence, which still uses whole-run hours.

 A3  ONLY THE CEV SIDE OF THE PLANT IS STOCHASTIC.
     apply_and_simulate! advances the MCS by soe_mcs[m] = value(SOE_MCS[m, g0+1]) -- the
     PLANNED value -- while the CEVs are advanced by the sampled draw. So MCS energy,
     grid draw, travel loss and therefore every cost term follow the plan exactly; the
     disturbance enters only through CEV depletion, and reaches the cost only indirectly
     (via what the next re-solve decides to do about it). Deliberate scope choice, but
     "the stochastic plant" should not be read as "everything is stochastic".

 A4  rest_cap USES round(), math_model.tex SAID ceil().
     Code: rest_cap = Int(round(t_limit_rest / delta_T)). At the defaults both give 4;
     they diverge for any t_limit_rest that is not a whole multiple of delta_T.
     math_model.tex corrected to round().

 A5  TWO SLACK VARIABLES ARE DECLARED BUT NEVER CONSTRAINED.
     s_miss_work is declared over [N_c, B] (all four activities) and the objective sums
     all four, but only dig and load appear in a balance. The travel/idle entries are free
     >= 0 variables carrying a positive cost, so the minimisation drives them to 0 and the
     result is unaffected -- dead variables, not a missing quota. Note the source PDF's
     objective has the same quirk (it sums s_miss over all a in A while (12c) constrains
     only a in A_con), so this mirrors the paper rather than departing from it.

 A6  y_trv[m,i,i,k] IS NEVER DEFINED.
     The y_trv == sum(x) definition loop skips i == j, but L_trv and the objective's
     labour term both sum over ALL (i,j) including i == j. Self-loop y is thus a free
     binary that only ever costs money and battery, so presolve fixes it to 0 -- benign,
     but it is |M|*|N|*|K| junk binaries and an easy trap when reading the model.

 A7  PRECEDENCE AND PACING READ THE SAME HISTORY THROUGH DIFFERENT AGGREGATIONS.
     Precedence seeds per SITE, pacing seeds per CEV. Both correct while A[i,e] is a
     one-to-one assignment, which it is in both datasets. Latent issue if a site ever
     gets two CEVs.

 A8  RECONCILED AGAINST THE SOURCE PDF (Optimization.pdf): (1), (2a-2f), (3a-3d),
     (4a-4c), (5a), (5e), (6a-6b), (7a-7b), (8c-8d), (9a-9b), (10a-10c), (10e),
     (11a-11c), (11e), (12a-12b), (12d), (12e), (13a-13b) all match. The 4-activity
     encoding is provably equivalent to the PDF's 3-activity (5d). Two accepted
     deviations, both MPC adaptations rather than errors (user-confirmed):
       - (11d) the PDF writes sum_t beta_arr = sum_t beta_dep per node; the code writes
         the generalised telescoping identity sum(beta_arr) - sum(beta_dep) =
         z[i,last(K)] - start_here, which is the correct form for a window that begins
         mid-route. KEPT AS IS.
       - (10d) the PDF requires each MCS to start the horizon at a grid node; the code
         pins the first interval to the carried-in node mcs_node0[m], which for windows
         after the first is legitimately a site. KEPT AS IS.

 NOTE: idle is a CONSTANT-power subactivity (paper Eq. 5e), pinned to 0 kW; there is
 NO separate shutdown/off state (a time-varying idle power is not part of the model).

=================================================================================
APPROACH 2 ADDENDUM -- stochastic (scenario-based) extension audit
=================================================================================
This file audits build_window_model (the deterministic MILP) as Approach 1 wrote it,
and every line above remains an accurate audit of that function -- it is UNCHANGED in
this codebase, still used verbatim for Approach 0's baseline. Approach 2 adds a SECOND,
sibling function, build_window_model_stochastic, in the same 3_MCSModel.jl file. This
addendum audits ONLY the delta.

WHAT'S MECHANICALLY IDENTICAL to build_window_model, per scenario copy s=1..S:
  - every @variable declaration (same families, +1 trailing scenario axis)
  - every @constraint (same math, `s in S_scen` added to the index set, and every
    variable reference gains a trailing `, s`)
  - the objective structure (sum of the same 6 cost terms), now weighted-averaged
    across scenarios: sum(w[s] * cost_s for s in S_scen), w = equal_weights(nS)
  - p_activity becomes p_activity_s[s] = Dict(B[a] => scenarios[s][a] ...), i.e. the
    ONLY substitution inside constraint math is mu -> scenarios[s] in the Eq 5e
    work-power identity; nothing else about any constraint's algebra changed.

WHAT'S NEW: a block of non-anticipativity @constraint calls, added AFTER the model is
otherwise fully built, immediately before optimize!(model). Audited family-by-family
against the "TIED at k0" list documented in docs/README.md Sec 13.2 (the
3_MCSModel.jl table row):
  u, mu(charge-permission), rho, z, g_ch, x, y_trv, beta_arr, beta_dep  -- all tied
  P_ch_MCS, P_MCS_CEV, P_dch_MCS, P_ch_tot, P_dch_tot, L_trv, L_trv_tot -- all tied
  P_work, SOE_CEV                                                       -- NOT tied (by design)
  s_miss_work, P_peak_NC, P_peak_OP, SOE_MCS                            -- NOT tied (by design;
                                                                           SOE_MCS comes out
                                                                           equal anyway, see below)
Verified: every family in the "tied" list appears in the deterministic model's own
variable list (cross-checked against the @variable block above in this same audit) --
no family was invented or omitted. P_work and SOE_CEV are deliberately excluded; forcing
them equal across scenarios would be a MODELLING BUG (it would make the hedging
mechanism vacuous -- see docs/README.md Sec 13.2 and Understanding_Stochastic_MPC.md's
worked example, where the whole point is that "Dig" costs a different amount of energy
per scenario despite being the same committed action).

SOE_MCS is NOT given an explicit non-anticipativity constraint, and this is INTENTIONAL,
not an oversight: its one-step recursion (this file's SOE_MCS[m,k+1,s] == ... equation)
at k0 references only P_ch_tot[m,k0,s] and P_dch_tot[m,k0,s], BOTH of which ARE tied, so
SOE_MCS[m,k0+1,s] is already forced equal across s by the existing recursion equality --
adding a redundant explicit tie would not change the feasible region, only add slack rows.
This matches this file's own recorded note above that only the CEV side of the plant (and
here, of the plan itself) is stochastic.

n_scenarios (S): plumbed from ScenarioSampler.jl's DEFAULT_N_SCENARIOS = 5 through
run_scenario_1 -> run_mpc -> build_window_model_stochastic. At S=1 the non-anticipativity
block is skipped entirely (`if nS > 1`) and the model is mathematically identical to
build_window_model with pvec = scenarios[1] -- i.e. S=1 recovers the deterministic model
exactly, which is the intended degenerate case and a useful sanity check if ever needed.

RNG separation (audited): run_mpc's scenario draws use `rng_scenarios =
MersenneTwister(seed + 1_000_000)`, constructed separately from `rng = MersenneTwister(seed)`
(the plant's own within-interval-split RNG) and from `cursor`/`pool` (the shared
ActivityPowerPool). No code path passes rng_scenarios into apply_and_simulate_stochastic!
or into next_power!, and no code path passes `rng`/`cursor` into sample_scenarios --
confirmed by grep across 4_MPCLoop.jl. Scenario draws are therefore provably unable to
consume or perturb the shared pool that Approach 0 also draws from, preserving the
like-for-like comparison this whole audit file already establishes was the point of the
shared-pool design for Approach 0 vs Approach 1 (now Approach 2).
